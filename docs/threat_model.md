# AndroMac (Bridge) — Модель угроз (Threat Model v1)

## 1. Введение и назначение документа

Документ определяет архитектурные границы доверия, классификацию защищаемых активов, векторы атак, профили потенциальных нарушителей и компенсирующие меры безопасности для системы интеграции **AndroMac (Bridge)**.

Основной постулат продукта: **Local-First & Privacy-First**. Система передает конфиденциальные данные (буфер обмена, SMS, уведомления приложений, коды двухфакторной аутентификации 2FA/OTP, поток экрана) исключительно по локальной вычислительной сети (LAN) напрямую между Android и macOS без использования облачных серверов, внешних прокси или сторонних учетных записей.

### Границы доверия:
1. **Зона устройства macOS (Trust Boundary 1)**: Защищена правами локального пользователя, песочницей и macOS Keychain.
2. **Зона устройства Android (Trust Boundary 2)**: Защищена механизмами безопасности Android (Linux UID isolation, SELinux, Android KeyStore).
3. **Недоверенная транспортная среда (Untrusted Network)**: Локальная Wi-Fi/Ethernet сеть. Предполагается, что к сети могут иметь доступ сторонние лица, открытые хотспоты (гостиницы, кафе, общественные сети), а также скомпрометированные сетевые маршрутизаторы.

## 4. Модель угроз (STRIDE Анализ)

### 4.1 Spoofing (Подделка личности)
- **Угроза**: Злоумышленник в локальной сети анонсирует поддельный mDNS сервис `_bridge._tcp` с целью перехвата соединения при первоначальном сопряжении или реконнекте.
- **Компенсирующие меры**:
  - Сопряжение выполняется строго через одноразовый **QR-код** или ручной защищенный канал.
  - В QR-код включаются SHA-256 отпечаток сертификата пира и криптографическая соль (TTL 60 секунд).
  - Обязательная визуальная верификация **Short Authentication String (SAS)**: 6-значный код (`123-456`) и 4-эмодзи последовательность.
  - Сохранение отпечатка в `CertificatePinStore` (Trust-On-First-Use с явным подтверждением). Любой сертификат с отличающимся отпечатком немедленно разрывает TCP/TLS хэндшейк.

### 4.2 Tampering (Фальсификация данных)
- **Угроза**: Модификация пакетов в транзите (внедрение вредоносного текста в буфер обмена, подделка команд управления экраном).
- **Компенсирующие меры**:
  - Шифрование канала через **mTLS** (TLS 1.3 / AES-GCM-256) предотвращает любую подмену данных в транзите.
  - Проверка целостности передаваемых файлов: каждый файл сопровождается SHA-256 дайджестом, который верифицируется блочно и целиком перед сохранением на диск.

### 4.3 Repudiation (Отказ от авторства)
- **Угроза**: Отправка неавторизованных команд (например, отправка SMS) без возможности определить источник.
- **Компенсирующие меры**:
  - Каждое сообщение упаковано в строгий конверт `Envelope` с монотонным идентификатором ULID, меткой времени `ts` и идентификатором отправителя.
  - Корреляция команд и подтверждений (`clientMessageId`, `ref`).

### 4.4 Information Disclosure (Утечка информации)
- **Угроза 1**: Пассивный перехват незашифрованного Wi-Fi трафика в публичной сети.
  - **Мера**: 100% трафика инкапсулировано в TLS-туннель. Незашифрованные порты не открываются.
- **Угроза 2**: Утечка чувствительных данных через системные журналы (logcat, syslog, консоль).
  - **Мера**: **Архитектурный инвариант Zero-Log PII**. Тексты SMS, пароли, OTP-коды и содержимое буфера обмена категорически запрещено передавать в методы логирования `print()`, `Log.d()`, `NSLog()`.

### 4.5 Denial of Service (Отказ в обслуживании)
- **Угроза**: Флуд пакетами WebSocket, вызывающий исчерпание памяти или батареи телефона.
  - **Компенсирующие меры**:
    - Сервер принимает соединения только от сопряженного доверенного сертификата.
    - Ограничение размера конверта и чанков (64 КиБ для файлов).
    - Ограничение размера очереди истории буфера обмена (FIFO, 20 элементов).
    - Тайм-аут пинга 15 секунд; автоматический разрыв сессии после 2 пропущенных понгов (30 с).

### 4.6 Elevation of Privilege (Повышение привилегий)
- **Угроза**: Эксплуатация механизма удаленного ввода (`remote.control.input`) для обхода экрана блокировки или нажатия разрешений безопасности.
- **Компенсирующие меры**:
  - Доступ к экрану и вводу активируется только при явном подтверждении на телефоне (Wireless Debugging / ADB pairing).
  - Защищенные системные окна (`FLAG_SECURE`) на уровне ОС блокируют захват экрана.

## 5. Политика хранения данных в покое (Data at Rest)

1. **Криптографические ключи**:
   - macOS: `macOS Keychain Services` с атрибутом доступности `kSecAttrAccessibleAfterFirstUnlock`.
   - Android: `AndroidKeyStore` с защитой аппаратным модулем (StrongBox / TEE).
2. **Кэш сообщений и уведомлений**:
   - Локальные базы данных шифруются с помощью **SQLCipher** (AES-256).
   - Ключ шифрования базы генерируется криптографически стойким генератором (CSPRNG) и помещается в защищенное хранилище ОС.

## 6. Чек-лист безопасности для Pull Request (Security Gate)

При каждом код-ревью Team Lead проверяет:
- [ ] Отсутствие логирования конфиденциальных данных (SMS, буфер, токены, OTP).
- [ ] Наличие валидации входящих конвертов и полей.
- [ ] Наличие пиннинга сертификатов при установлении соединения.
- [ ] Очистку чувствительных данных в памяти при отключении пира.
- [ ] Отсутствие передачи данных на сторонние внешние хосты в интернете.
